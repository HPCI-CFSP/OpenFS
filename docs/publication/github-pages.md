# GitHub Pages Publication

## Why GitHub Pages

OpenFS outputs are versioned public artifacts already stored in GitHub. A static Pages site provides a low-maintenance, reviewable view of the research catalog, curated public research summaries, accepted roadmap scenarios, and accepted reports without operating an application server or exposing repository write credentials to a web service.

The site builder reads only explicitly approved public paths. It does not directly publish proposals, assessments, runs, reviews, internal material, or illustrative scenarios. Topic summaries are curated public-only projections under `knowledge/public/`; they retain provisional and Consensus status and are not canonical Claims or HPCI recommendations. Every published artifact must have `status: published`, explicit public-classification metadata, a Publication Decision ID, required Japanese and English fields, and a matching human-authored `publication-approval` Directive under `reviews/directives/`. The builder copies only allowlisted public fields rather than serializing the source object as-is. The public view is generated by `tools/build_pages_site.py` under `config/publication-policy.json`.

## Repository implementation

- `site/`: static HTML, CSS, and JavaScript.
- `tools/build_pages_site.py`: creates `_site/` and public data from approved inputs.
- `.github/workflows/pages.yml`: validates, builds, uploads, and deploys the site.
- `.github/workflows/pages-preview.yml`: builds a non-deployed review artifact for
  same-repository pull requests that change Pages inputs.
- `roadmaps/scenarios/accepted/`: future Publication-Gate-approved scenario inputs.
- `reports/exports/index.json`: future Publication-Gate-approved report index.
- `config/publication-i18n.json`: English Topic names and Japanese technology-landscape labels used by the bilingual public projection.
- `knowledge/public/topic-summaries.json`: approved bilingual research summaries, provisional status, selected findings, and public source links shown from each Topic.
- `knowledge/public/consensus-receipts.json`: approved public proof records for accepted Findings. Each Receipt lists the participating model and Agent identities, independence groups, Consensus policy result, harness repository, Run ID, and exact harness commit SHA without exposing raw Assessments or private Run content.

The project site is `https://hpci-cfsp.github.io/OpenFS/`. Visitors can switch between Japanese and English; the selected language is retained locally in the browser.

## One-time actions for a repository administrator

1. Open `HPCI-CFSP/OpenFS` on GitHub.
2. Select **Settings** → **Pages**.
3. Under **Build and deployment**, set **Source** to **GitHub Actions**.
4. Select **Settings** → **Secrets and variables** → **Actions** → **Variables**.
5. Add repository variable `OPENFS_PAGES_ENABLED` with value `true`.
6. Open **Actions** → **Publish OpenFS Pages** → **Run workflow** for the first deployment.
7. Confirm the `github-pages` Environment permits deployment only from the default branch. Add a protection rule if the Organization policy requires it.

No API key, personal access token, DNS setting, or separate hosting account is required for the default `github.io` URL. A custom domain can be added later in Pages settings and DNS.

## Publication approval

Before adding a Topic Summary, Consensus Receipt, Scenario, or Report to Pages:

1. Prepare both Japanese and English public titles and summaries.
2. Confirm that every field is suitable for public release.
3. Create a human Directive with `directive_type: publication-approval`, status `approved` or `completed`, and the exact Export, Scenario, or Report IDs under `publication_targets`.
4. Reference that Directive from `publication.human_approval_directive_id` in each artifact.
5. Let CI build the public projection. Missing or mismatched approval causes the build to fail closed.

For an accepted Finding, also add `consensus_receipt_id` and publish the matching
Receipt. The Receipt must identify an accepted Decision, at least two actual
voting model identities, at least two voting independence groups, every public
model/Agent participant, and at least one harness with a full 40-character
commit SHA. Multiple Agent IDs backed by one model identity do not satisfy this
publication check. A provisional Finding cannot
carry a Receipt. Pages renders the Receipt behind a clickable Consensus proof
line so visitors can inspect the model, Agent, policy, harness, Run, and commit
used for the decision.

## Safe activation

Pushes do not deploy until `OPENFS_PAGES_ENABLED=true`. Manual `workflow_dispatch` is allowed so an administrator can test the first deployment. The generated site shows no candidate roadmap or report until published and human-approved artifacts exist. A Topic row always opens a detail view; Topics without an approved summary show a clear pending state.

## Local build

```bash
python3 tools/build_pages_site.py --output _site
```

Open `_site/index.html` directly or serve `_site/` with a local static server. The generated `_site/` directory is disposable build output and is not committed.

## Pull-request preview before merge

GitHub's official `actions/deploy-pages` PR-preview input is not publicly
available. OpenFS therefore does not deploy a PR over the production Pages site.
For a same-repository PR that changes a Pages input:

1. Wait for **Build OpenFS Pages Preview** to pass.
2. Open that workflow run from the PR Checks tab.
3. Download `openfs-pages-preview-pr-<PR number>` from **Artifacts**.
4. Extract it and open `index.html`, or serve the directory with
   `python3 -m http.server 8000 --directory <directory>`.
5. Check Japanese/English switching, the Technology landscape tab, desktop and
   mobile widths, and confirm that no candidate Scenario or Report is exposed.

The Preview job has only `contents: read`. It does not request `pages: write` or
`id-token: write`, does not call `actions/deploy-pages`, and retains the artifact
for 14 days. Pull requests from forks are skipped because their proposed code is
not executed by this preview job. A shareable hosted PR URL would require a
separate preview hosting service or repository and a separate security review.
